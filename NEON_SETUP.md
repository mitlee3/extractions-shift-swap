# Connect this backend to Neon

The Express backend uses `pg` to connect to Neon PostgreSQL. It reads the database URL from `DATABASE_URL` and queries the existing `"ShiftSwaps"` and `"User"` tables.

## Configure the connection

1. In Neon, copy the connection string for your database. Use the pooled connection string for deployed workloads when available; the connection string should use TLS (`sslmode=require`).
2. Set it as `DATABASE_URL` in the deployment platform's environment variables or secret manager. Keep it secret; do not commit it to Git or expose it in browser-side code.
3. Keep the existing `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `OAUTH_REDIRECT_URL`, and `SESSION_SECRET` environment variables configured as before.
4. Install dependencies and start the app:

```sh
npm install
npm start
```

For local development, set `DATABASE_URL` in your shell or in an ignored `.env` file using an environment-variable loader. Do not paste the real connection string into source code.

## First-time user profiles

After Google sign-in, the app looks up the verified email in `"User"` case-insensitively. Existing users continue to the dashboard. New users are prompted to complete a profile; their verified email is supplied by Google and the UUID `id` and `created_at` are generated by PostgreSQL. The profile form collects first and last name, position, shift days, and shift number, then inserts the row into `"User"` and redirects to the dashboard.

Position and shift number dropdown choices have defaults. Set `PROFILE_POSITIONS` and `PROFILE_SHIFT_NUMBERS` as comma-separated environment variables to use values matching your organization. Shift-day options are weekdays; users can select multiple days and those are stored as a comma-separated string in `shift_days`.

There is no user-entered date in the supplied `"User"` schema: `created_at` is set automatically. The calendar date fields belong to `"ShiftSwaps"` and are not part of this onboarding form.

## Dashboard data

The authenticated `GET /api/shift-requests` endpoint joins each `"ShiftSwaps"` row to the requesting user and, when present, the offering user in `"User"`. The dashboard displays those names, the two requested dates, and the status. `Requesting` is counted as pending. `ShiftSwapsIndividual` is not currently queried, and swap creation or updates are not implemented.
